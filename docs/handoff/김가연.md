> **디자인은 신경 쓰지 않아도 됩니다.** 모든 기능이 끝난 뒤 최원준이 새로 합니다. 기능이 동작하고 화면에 보이기만 하면 됩니다.

> **시간이 정해져 있습니다.** 가능한 시간은 **목요일 16:00 이후**, **금요일 점심~저녁(2시간 이상)**, **토요일 MT 복귀 후**, **일요일 16:00 이전**입니다. **일요일 16시 이후에는 개발 지원이 어려우므로, PR은 토요일 20:00까지 올려서** 최원준이 토요일 밤에 merge할 수 있게 해 주세요. 공통 규칙은 [README.md](README.md)를 보세요.

> 일정은 각자 유동적으로 바꿔도 됩니다. 다른 사람이 기다리는 전달 기한이 바뀌면 단톡방에 미리 알려 주세요.

## 시작 전 준비

1. 저장소 Collaborator 초대 수락 → 위 README의 실행 방법대로 로컬 실행
2. `python -m pytest` 가 모두 통과하는지 확인
3. 작업마다 새 브랜치 (아래 "PR 순서" 체인 참고): 첫 브랜치만 `git switch main && git pull && git switch -c feature/location`
4. 끝나면 push → GitHub에서 PR → 최원준 확인 후 merge
5. 파이썬 파일을 고치면 맨 위 `버전 기록`에 한 줄 추가 (예: `# v0.4 (2026-11-19) 현재 위치 반영`)

## PR 순서 (한 줄로 이어서 쌓기)

금·토에는 최원준이 merge할 수 없으므로, **앞 브랜치에서 다음 브랜치를 따서 이어 쌓습니다.** 같은 사람이 이어 쌓기 때문에 충돌하지 않고, 최원준은 토요일 밤에 순서대로 merge합니다.

```
main ← feature/location (PR-1a, 목)
        ← feature/name-en (PR-1b, 목)           ← location에서 분기
            ← feature/naver-map (PR-M, 금)       ← name-en에서 분기
                ← feature/dong-chips (PR-2, 토)   ← naver-map에서 분기
```

- PR-1b를 목요일에 못 하면 `feature/naver-map`을 `feature/location`에서 바로 분기해도 됩니다.
- PR을 올릴 때 **base 브랜치를 앞 PR의 브랜치로** 지정하고, PR 설명 맨 위에 "앞 PR: #번호"를 적습니다.
- 토요일 20:00까지 PR-2를 못 끝내면 일부만 올려도 됩니다 (**앞 PR들은 이미 merge 대상이라 영향 없음**). 일요일에 마무리해야 하면 merge가 끝난 새 `main`에서 11:00까지 새로 시작합니다.

## Git 규칙 (충돌 방지)

- `git add -A` 금지. **바꾼 파일 이름을 지정해서** `git add` (`data/places.json`, `trippin.db`, `.env`가 실수로 올라가면 안 됨)
- `data/places.json`은 **절대 커밋하지 않기** (최원준만 만듦)
- **네이버 지도 키는 코드·문서·PR 설명·커밋 어디에도 쓰지 않기.** 환경 변수 `NAVER_MAP_CLIENT_ID`로만 읽기
- `i18n/*.json`: **`origin_note`와 내가 새로 만드는 키만** 4개 언어 파일에 추가. 기존 키는 수정하지 않기. PR 설명에 새 키 목록을 적기.
- 건드리는 파일은 아래 "건드리는 파일" 칸만. 다른 파일을 바꿔야 하면 최원준에게 먼저 물어보기
